# SPEC：本插件的规格驱动开发流程

> 状态：已采纳（2026-10-19）。适用于本仓库所有 **M / L 级改动**。
> 一句话：**先写清「为什么做、做到什么算完」，再写「怎么做」；每条验收标准都必须有可执行的验证方式。**

---

## 0. 我们不是从零开始

本仓库已经有一套很强的工程文档和闸门。SPEC **不重复它们**，只补上「按次改动」这一层：

| 已有资产 | 回答的问题 | 引入 SPEC 后的位置 |
| --- | --- | --- |
| `AGENTS.md` | Agent 开工必须遵守什么（硬约束、命令、红线） | 不变；新增「改动分级与 SPEC」入口 |
| [`docs/插件化架构说明.md`](../docs/插件化架构说明.md) | 目标架构、模块边界、契约 | 不变；spec 的「影响面与约束」引用它，不抄写 |
| [`docs/插件设计文档.md`](../docs/插件设计文档.md) | 代码为什么这么写、哪里不能碰、怎么发布 | 不变；每个 spec 完成后把**新知识**沉淀回这里 |
| [`docs/插件化迁移计划.md`](../docs/插件化迁移计划.md) | 一次性的插件化迁移历史 | 冻结为历史记录，不再新增阶段 |
| `tools/checks/`（39 项） | 哪些逻辑与流程已经被自动守住 | 不变；spec 的自动验收优先复用或新增这里的检查 |
| `tools/release.sh` | 发布前自检、构建、打包 | 不变；`npm run verify` 会带上 `spec:check` |
| `specs/`（本目录） | **这一次改动为什么做、做到什么算完** | 新增 |

为什么值得多这一层：现有文档回答的是「系统整体怎么运转」，回答不了「**这次**改动的边界在哪、
什么算做完」。没有这一层时，需求只存在于对话和提交信息里，验收标准要等实现完才补，
Agent 只能靠猜；出了问题也说不清是「没做」还是「没验」。

## 1. 先决定：这次改动要不要写 spec

| 级别 | 判定 | 需要什么 |
| --- | --- | --- |
| **S** | 不改变用户可见行为，也不动数据 / 设置 / 持久化 / 命令面 / 样式结构。例：改错字、改注释、单行 bug 修复且回归路径明确、纯文档、检查脚本自身的修正 | **不用 spec**。提交信息里写一句为什么算 S |
| **M** | 单模块内的用户可见行为变化、单个设置项、单个交互、单条样式修正、新增一项检查 | `spec.md` + `tasks.md`（两件套） |
| **L** | 新 Feature Module / Service、跨模块改动、`data.json` 结构或设置默认值变化、发布级重构、换肤级样式改版、需要多路径人工回归的改动 | `spec.md` + `plan.md` + `tasks.md`（三件套） |

- 判断不准就**升一级**：宁可多写半页 spec，不要事后补。
- 紧急热修可以先修后补，但必须在 24 小时内补成 `status: verifying`，并在「评审记录」里写 `backfill`。
- **S 不是漏洞**：如果一次「小修」最终动了行为、数据或样式结构，它就已经不是 S，补 spec。

## 2. 目录与命名

```text
specs/
├── README.md                  ← 本文件：流程、分级、状态机、命令
├── constitution.md            ← 不可协商条款索引（写 spec 前先读）
├── _template/                 ← 模板（不要改结构，改之前先跑 spec:check 确认）
│   ├── spec.md
│   ├── plan.md                ← 仅 L 级使用
│   └── tasks.md
├── archive/                   ← done / dropped 后移到这里
└── 001-<slug>/                ← 一次改动一个目录
    ├── spec.md
    ├── plan.md                ← 仅 L 级
    └── tasks.md
```

- 编号三位递增、**不复用**；编号与目录名、frontmatter 的 `id` 三者一致。删掉 / 合并规格会留空号，**允许**（门禁只查重复与格式，不要求连续）。
- `slug` 用小写英文与连字符（`theme-tone-contrast`），便于 git / 命令行操作；标题用中文。
- 目录名格式：`^\d{3}-[a-z0-9]+(?:-[a-z0-9]+)*$`（slug 不含首尾 / 连续连字符）；编号从 `001` 起。
- 规格完成后 `git mv specs/001-xxx specs/archive/001-xxx`；**编号与内容都不改**，只改位置和状态。

## 3. 三个文件各写什么

| 文件 | 回答的问题 | 不该写什么 |
| --- | --- | --- |
| `spec.md` | **为什么做（问题与动机）、给谁做（用户场景）、做什么（需求）、做到什么算完（验收标准）** | 实现细节、文件清单、代码方案（这些放 `plan.md`） |
| `plan.md`（L） | **怎么做**：只写三节——方案概述（含模块归属 / 数据 / 淘汰方案）、影响与兼容（含风险回退）、实施与验证顺序 | 需求与验收（这些在 `spec.md`） |
| `tasks.md` | **拆成哪些可勾选的任务、每项验收的证据、要更新哪些长期文档** | 长篇背景（这些在 spec / plan） |

三个硬约定：

1. **ID 可追踪**：需求 `FR-001`、非功能需求 `NFR-001`、验收标准 `AC-001`、任务 `T-001`。
   每条 AC 必须被至少一条任务覆盖；每个 FR 必须被至少一条任务覆盖。
2. **验收标准必须可判定**：要么指向一个真实存在的自动检查（`tools/checks/check-*.js`），
   要么写成照着就能做的人工步骤（进 Obsidian 点哪里、看什么）。不许写「检查一下是否正常」。
3. **长期知识不留在 spec 里**：实现过程中发现的坑、约定、架构变化，收尾时沉淀回
   `docs/插件设计文档.md` / `docs/插件化架构说明.md` / `AGENTS.md`，并在 `tasks.md` 的
   「文档更新」里逐项勾掉。

## 4. 状态机与每道门槛

```text
draft ──评审通过──> approved ──开始实现──> implementing ──实现完成──> verifying ──验收完成──> done
  │                    │                     │                      │
  └────────────────────┴─────────────────────┴──────────────────────┴──────────────> dropped
```

| 状态 | 必须满足（`npm run spec:check` 会检查） | 谁推进 |
| --- | --- | --- |
| `draft` | 目录与 frontmatter 合法；「一句话」与「问题与动机」是**实写**的（模板注释不算） | 提出人 |
| `approved` | `spec.md` 章节齐全且有实质内容、FR / NFR / AC 内容非空、每条 AC 的验证方式按「自动：/人工：」分段；`tasks.md` 覆盖全部 FR / AC；无占位符残留（`{{…}}` / TODO / TBD） | 人评审 |
| `implementing` | 同 `approved`；任务可以未勾 | 实现者 |
| `verifying` | 任务**全部勾选**；至少 1 条自动验收证据已勾选并写清结果 | 实现者 |
| `done` | 验收证据（≥2 条）与文档更新**全部勾选**，且证据不是空话；AC 引用过 `check-*.js` 的，证据里必须有「反向验证」；已移到 `specs/archive/` | 实现者 |
| `dropped` | frontmatter 写 `dropped_reason`；已移到 `specs/archive/` | 提出人 |

- 状态**只前进**：`draft → approved → implementing → verifying → done`。回退要改状态并在评审记录里写明原因。
- `approved` 之后**需求变了先改 spec**，在评审记录补一行，再改代码。不要用代码「顺便」实现没写进 spec 的东西。
- `check-specs` 会拦下列情况：目录名 / 编号重复、frontmatter 字段非法或日期不存在、
  `related` 指向仓库外（含符号链接绕行）或不是文件、状态与 archive 位置不一致、根与 archive 里的散装文件、
  占位符残留（含大小写变体）、章节空着或只有模板注释、代码围栏里藏的表格不算数、
  需求 / 验收表里有格式不合法的 ID 行（`AC-01`、无 ID 行等）、FR / NFR / AC 内容为空、
  AC 没按「自动：/人工：」分段、自动项不是白名单脚本或 `tools/checks/check-*.js` 完整路径、
  自动项指向不存在或**在 `run-all.sh` 里被注释掉**的检查、人工项少于 20 字或写成「检查一下是否正常」、
  任务引用不存在的 ID / 内容为空、有 FR / AC 没被非 CHORE 任务覆盖、L 级缺 `plan.md`、
  `verifying` 没有已勾选且写清「跑了什么 + 什么结果」的自动证据、
  `done` 还有未勾选项或证据是空话、动过自动检查却没有「反向验证」证据。
### 4.1 门禁能保证什么、不能保证什么

**能拦下的**（都有反向验证用例兜着）：结构缺失、编号重复、frontmatter 非法、占位符残留、
章节空着或只有模板注释、需求 / 验收为空、ID 行格式不合法、自动项指向不存在或没被
`run-all.sh` 执行的检查、自动项引用非白名单脚本、人工项写成空话、证据没写「跑了什么 + 什么结果」、
证据是「未通过 / 不一致」这类否定结论、`verifying` 没有已勾选的自动证据、`done` 还有未勾选项、
动过自动检查却没有反向验证证据、`related` 越界或指向目录、归档位置不对。

**不能保证的**（别把门禁当护身符）：

- **不能证明命令真的跑过**。证据里写「`npm run verify` → 全绿」，门禁只检查这句话的形式是否合格；
  真实结果要靠复跑——发布时 `tools/release.sh` 会真的执行 verify 与构建。
- **不能判断需求是否值得做、验收标准是否合理**，那是评审。
- **不能证明「每个 M / L 改动都有 spec」**：它只对「工作区改动的文件是否被在途规格提到」打印提示，不阻断。
- **挡不住故意伪造**：静态规则越细，绕过越隐蔽，最后只会把成本转嫁给写文档的人。门禁的目标是把
  「忘了写、写了空话、证据没落地」这类**无意疏漏**拦在提交前；真正的防线是评审 + 复跑 + 归档后的可追溯。

**解析口径**（写 spec 时按这个来，否则可能被判红或漏检）：

- ID 表要带外框竖线（`| ID | … |`）和分隔行；**无外框的 GFM 表格不参与解析**。
- 代码围栏（``` / ~~~）里的内容不参与解析（可以放示例代码），围栏要成对闭合。
- 验证方式按 `；` 分段，每段以 `自动：` / `人工：` 开头；段内不要再藏第二个标记。
- `related` 的大小写按当前文件系统判定（macOS 不区分、Linux 区分），跨平台请写与文件一致的大小写。
- 反向验证开关 `WT_SPECS_ROOT` / `WT_THEME_CSS` 只用于本地实验；`tools/release.sh` 会在跑任何检查前
  清掉它们，避免发布的检查被重定向到副本。

## 5. 一次改动的完整流程

```text
① 判定级别（S / M / L）
② M / L：npm run spec:new -- <slug> "<标题>" --size M|L
   （刚建出来时 spec:check 是红的——draft 也要求「一句话」与问题动机实写，这是有意的）
③ 写 spec.md：问题动机 → 用户场景 → 需求 → 验收标准 → 非目标 → 影响面
④ 评审：人确认 scope 与验收标准；status 改 approved，评审记录补一行
⑤ L 级补 plan.md；两件套 / 三件套都补 tasks.md（任务要能映射到 FR / AC）
⑥ 实现：勾任务；需求变化先改 spec；一步一提交，提交信息带 spec 编号
⑦ 验证：npm run check / build / verify + 人工回归 + 新增检查的反向验证
⑧ 收尾：填验收证据；更新长期文档；status 改 done；git mv 到 archive
```

### 5.1 提交信息约定

```text
feat(spec-001): 高对比度换 Notion 皮肤
fix(spec-001): 窄屏下拉 flex-basis 改回 auto
docs: 补充 SPEC 说明（S，无 spec）
```

- 带 spec 的改动：`<type>(spec-NNN): …`；`type` 沿用现有习惯（`feat` / `fix` / `docs` / `style` / `refactor` / `chore`）。
- S 级改动：照常写清做了什么、为什么不需要 spec。

### 5.2 发布时

- `tools/release.sh` 会跑 `npm run verify`（包含 `spec:check`），并在打包前单独跑一次
  `node tools/checks/check-specs.js --pending`：**还有 `implementing` / `verifying` 的规格就拦下发布**。
  确认与本次发布无关时，用 `--allow-pending-spec` 显式放行。
- `draft` / `approved` 不拦（那是还没开始做的工作）。
- `--skip-verify` 会绕过 verify（连同其中的 `spec:check`），但打包前的 `--pending` 闸门仍会跑；只在应急时用。

## 6. 命令

```bash
npm run spec:new -- <slug> "<标题>" [--size M|L]   # 建新规格，自动取下一个编号并套模板
npm run spec:check                                 # 校验全部规格（verify 已包含）
npm run spec:list                                  # 列出当前规格与状态
```

`spec:new` 只创建**空模板**（状态 `draft`）；它不会替你写需求，也不会把状态推进到 `approved`。
创建成功后 `spec:check` **预期是红的**，直到你写完「一句话」与「问题与动机」——半成品规格不该全绿。
`check-specs.js` 支持用 `WT_SPECS_ROOT` 指向一份临时副本，用来做反向验证（见脚本顶部注释）。

## 7. 写验收标准的具体要求

本插件**没有测试框架**（见设计文档 §4.9）。验收标准因此分两类，缺一不可：

| 类型 | 写法 | 要求 |
| --- | --- | --- |
| **自动** | `自动：\`tools/checks/check-xxx.js\`` | 检查必须真实存在；新写的检查必须做一次**反向验证**（把修复改回坏的样子，确认它会变红），并在 `tasks.md` 证据里写结果 |
| **人工** | `人工：Obsidian 中打开设置 → 排版 → 切到高对比度，看设置行分割线是否为直线` | 写成可照做的路径与观察点；覆盖渲染、布局、主题、输入法、移动端这些自动检查验证不了的部分 |

- 验证方式列按 `；` 分段，**每段必须以「自动：」或「人工：」开头**（不做子串猜测，避免「自动保存」被误判）。
- 自动项要么写完整路径 `tools/checks/check-*.js`（必须存在于 `run-all.sh` 的 `CHECKS` 数组且**未被注释**），要么用白名单脚本 `npm run check / verify / spec:check / lint:gate`（`dev` 常驻、`release` 会打包，都不许当验收）。
- 改过自动检查的规格，`tasks.md` 的证据里必须有一条**反向验证**（把修复改回坏的样子，确认检查变红）并在 `done` 前勾上。
- 人工项至少 20 个可见字符；证据里已勾选的自动项必须写清「跑了什么 + 什么结果」（含命令 / 检查名 + 数字或通过 / 变红等结论）；两者都**不许**写成「检查一下是否正常」「随便」「没问题」这类空话。
- 「；」只在后面紧跟 `自动：` / `人工：` 时才当分段（人工步骤里正常使用分号不受影响）。代码围栏（```）里的内容不参与解析，不许拿它藏验收标准或证据。
- 纯逻辑/存储层的改动至少要有自动检查；纯样式/渲染的改动至少要有具名人工路径。
- 「测试通过」不是验收标准；**「哪个检查、哪条路径、看到什么」**才是。

## 8. 红线

1. **不写空话**：没有开放问题就写「无」；不要用「优化体验」「提升稳定性」这种无法验收的句子。
2. **不抄长期文档**：约束只写「见宪法 #n / 设计文档 §x」，正文留在原文档，避免两份内容漂移。
3. **不写真实作品名 / 角色名**：本仓库公开，`tools/release-check.sh` 与 pre-commit 会拦；
   spec 里的示例一律用虚构名（与设计文档 §6.1 同一规则）。
4. **不把 spec 当日记**：只记录与这次改动有关的决策；过程流水账留在提交信息和对话里。
5. **不跳过人工回归**：渲染/布局/主题/输入法/移动端的改动，自动检查全绿也不算完。
