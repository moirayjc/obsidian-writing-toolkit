# 规格（spec）

> 状态：已采纳（2026-10-20），取代 2026-10-19 的三件套流程（旧记录见文末「历史」）。
>
> 一句话：**动手前需要作者拍板的改动，先写一页纸；只需要「写对」的改动，用检查和提交信息说话。**

---

## 1. 什么时候写

spec 解决的只有一件事：**在写代码之前，让作者和实现者（多半是 Agent）对「做什么、不做什么、怎么算完」达成一致。**
没有需要达成一致的东西，就不写。

| 写 | 不写 |
| --- | --- |
| 新增或删除一个用户看得见的功能、入口、视图 | 修 bug（哪怕用户看得见） |
| 改 `data.json` 的结构、设置项、默认值 | 重构、性能优化、补检查、改文档 |
| 改变已有交互，用户会察觉「跟以前不一样」 | 单条样式修正、文案修正 |
| 换肤级的样式改版 | 版本发布本身 |

拿不准时问一句：**「实现之前，需要作者确认要不要这样做吗？」** 需要就写，不需要就不写。

**不写 spec 的改动，提交信息就是记录**，要写清三件事：

```text
fix: 跨午夜保存把昨天的字数写进今天

现象：零点后、跨天结算前保存，今天的日期键拿到昨天的总数。
根因：savePluginData() 用实时日期作键，内存数值却属于 activeDay。
验证：新增 check-day-rollover.js（反向验证：改回旧写法 7 条变红）；
      verify 42 项全绿；跨午夜真机回归：已做 / 未做（未做就写未做）。
```

修 bug 时能写回归检查就写，并做反向验证（见 `AGENTS.md`）。这条对所有改动都成立，不是 spec 专属。

## 2. 怎么写

```bash
npm run spec:new -- <slug> "<标题>"    # 生成 specs/NNN-slug.md
```

一个 spec 就是**一个文件、一页纸**，六节，模板见 [`_template.md`](_template.md)：

| 节 | 写什么 |
| --- | --- |
| 一句话 | 改变什么、为谁改变 |
| 为什么 | 现在哪里不对；有用户原话、事故、代码位置就贴上 |
| 做什么 | 要做到的行为，逐条列。写**行为**，不写实现方案 |
| 不做什么 | 划清边界，防止实现时「顺手」多做。没有就写「无」 |
| 怎么算完 | 勾选清单，每条以「自动：」或「人工：」开头（见下） |
| 记录 | 每次确认、改范围、完成，各记一行日期 |

「怎么算完」的写法：

- **自动**：写检查脚本的完整路径 `tools/checks/check-xxx.js`，或 `npm run check / build / verify / lint:gate`。
  检查可以等实现时再写，但 spec 转 `done` 前它必须存在并注册进 `tools/checks/run-all.sh`。
- **人工**：写成照着就能做的步骤：进 Obsidian 点哪里、看到什么才算对。渲染、布局、主题、输入法、手机端只能靠这一类。
- 不许写「检查一下是否正常」「没问题」这种判断不了真假的话。

另外三条：约束只写章节号（「见设计文档 §4.1」），不要把长期文档抄进来；示例一律用虚构名；
不写过程流水账，那是提交信息和对话的事。

## 3. 状态与规矩

```text
draft ──作者确认 → 实现 → 清单全勾──> done
  └─────────────────────────────────> dropped（写明 dropped_reason）
```

只有三个状态，配三条规矩：

1. **作者确认之前，不写实现代码。** 确认时在「记录」里写一行：哪天、确认了什么（「同意方案 A」「范围去掉 X」）。
2. **范围变了，先改 spec 再改代码**，「记录」补一行。不用代码「顺便」实现 spec 里没写的东西。
3. **「怎么算完」全部勾上**，并把实现中发现的坑和约定沉淀进 `docs/插件设计文档.md`（或架构说明 / `AGENTS.md`），
   再把 `status` 改成 `done`。spec 文件留在原处，不移动。

提交信息带编号：`feat(spec-007): …`。发布不会因为还有 `draft` 被拦，`tools/release.sh` 只把清单打印出来提醒你。

## 4. 门禁管什么

`tools/checks/check-specs.js`（已在 `npm run verify` 里）只守**形式**：

- 文件名 `NNN-slug.md` 与 frontmatter 一致，编号不重复（包括 `archive/`）；
- 六节都在、都不是空的（只有模板注释也算空），没有残留 `{{…}}` 占位符；
- 「怎么算完」至少一条，每条以「自动：」或「人工：」开头，自动项指向检查脚本或白名单 npm 命令；
- `done` 的清单全部勾选，自动项指向的检查存在且确实被 `run-all.sh` 执行；`dropped` 写了理由。

它**不判断**需求值不值得做、清单够不够，也证明不了命令真的跑过。那是作者确认和复跑的事。
门禁故意只做这么多：规则越细，写 spec 的人越是在应付格式，而不是在想清楚问题。

`npm run spec:check` 单独跑门禁，`npm run spec:list` 列出全部 spec 与状态。
