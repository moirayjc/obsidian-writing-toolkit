# SPEC-005 · 桌面端读者手机预览

> 一句话：在桌面端给编辑台加一个**读者手机预览**——把「一键复制纯净正文」那份内容放进 390×844 / 360×800 的手机外框里，按阅读器的排版（段首缩进两格、行距、底纹、字号档位）显示出来，让作者在交稿前就能看到读者在手机上读到的样子。
>
> 分级：L ｜ 状态：done ｜ 创建：2026-10-19

## 1. 问题与动机

用户原话：

> 桌面端加个手机界面预览的功能，方便看小说上传后，在读者手机里是什么样一个状态。

这条链路上缺的正是最后一环。插件已经在做「写 → 交稿」这一半：编辑台有**一键复制纯净正文**（`src/main.ts` 的 `copyCleanChapter`），作者粘贴到平台后台即完成上传。但**上传之后读者看到的是什么样**，作者在桌面端完全看不到：

- 桌面编辑器的正文宽度通常在 700–1000px，一屏 40 字以上；手机阅读器只有 360–390px 宽，一屏 17–20 字。同一段文字，**断行位置、段落长度手感、对话密集段的观感**完全不同，而这些恰恰是网文读者最敏感的东西。
- 段落缩进与行距由阅读器决定，作者在 Obsidian 里看到的排版（跟随主题行距、无缩进）**不代表读者看到的排版**。
- 平台后台的预览往往要真的存草稿才看得到，改一版看一版成本高。

同时要说明**为什么不能靠现有的 `wt-mobile` 预览**：那是把**插件自己的界面**（主页/编辑台/工具箱的抽屉、底部导航、FAB）按手机布局呈现，看的是「作者的工具在手机上长什么样」；本 spec 要看的是「**读者的手机里，正文长什么样**」。两者目的不同，不能互相替代。

## 2. 用户场景

- 当我写完一章想确认手机上读起来会不会「一屏就两行、全是短段」时，我想在桌面端点一下就看到 390 宽的手机排版，以便决定要不要合并/拆分段落。
- 当我想检查「一整章连续读下来」的节奏时，我想在预览里直接点「下一章」往后翻，而不是回编辑器换一章再点一次预览。
- 当我想确认夜间模式下正文是否仍然清楚、米黄底纹是否更像阅读器时，我想在预览里切底纹与字号档位，以便选一个贴近目标平台观感的组合。
- 当我在真机上写作时，我不需要这个入口（人已经在手机上了），它不该占位置。

## 3. 需求

### 功能需求

| ID | 需求 | 优先级 |
| --- | --- | --- |
| FR-001 | 桌面端入口：编辑台书头新增手机图标按钮（悬停提示「手机预览本章」）；书头菜单与章节行右键/长按菜单各有一条「手机预览本章 / 手机预览这一章」；**真机（`Platform.isMobile`）不显示按钮与菜单项** | 必须 |
| FR-002 | 手机外框：**单一通用手机形态**（不分苹果 / 安卓），含机身圆角/边框、状态栏（时间与信号电池）、阅读器顶栏（章节名 + `第 N/M 章 · 本章 X 字`）、正文滚动区、阅读器底栏（上一章 / 章节信息 / 下一章）；外框按宽度比例（约 390:844）呈现，且**高度随窗口自适应，整台手机（含底栏）必须在一屏内可见**，不需要滚动弹窗才能看全 | 必须 |
| FR-003 | 内容一致：正文严格取自与「一键复制纯净正文」**同一条文本管线**（打开中的编辑器取实时文本，否则读文件），按行分段、段首缩进两格、段间留白；预览不改变文本内容 | 必须 |
| FR-004 | 阅读显示设置：字号四档（小 / 标准 / 大 / 特大）、底纹三种（白纸 / 米黄 / 夜间）；切换即时生效，且**只影响本次预览**，不写 `data.json`、不新增设置项 | 必须 |
| FR-005 | 翻章：底栏「上一章 / 下一章」在本书章节序列内前后翻，标题、章节序号与字数随之更新；首章/末章时对应按钮禁用；不在作品目录内的单篇文档也能预览（只是没有翻章） | 必须 |
| FR-006 | 交互与边界：正文区独立滚动；切字号/底纹/机型**不丢滚动位置**；`esc` 关闭；文档为空或文件不存在时给出提示而不是空白外框 | 必须 |

| ID | 需求 | 说明 |
| --- | --- | --- |

| NFR-002 | 不新增设置项、不改 `data.json` 结构与默认值；预览偏好只存在内存里 | 见宪法 #5 |
| NFR-003 | 不新建 Feature Module（`check-module-contract.js` 的 12 个模块契约保持不变）；UI Shell 只通过 `uiShellContext.ts` 的显式端口调用，不 import 实现 | 见宪法 #4、架构说明 §5 |
| NFR-004 | 预览**只读**：不写正文、不写伴随文件、不写 `data.json` | 见宪法 #2 的精神 |
| NFR-005 | 样式走 `--wt-*` 令牌，弹窗限定在桌面端；暗色与高对比度主题下手机框与工具栏不脏；不改动既有 `body.wt-mobile` 规则 | 见宪法 #8 |

## 5. 非目标

- **不做 Markdown 渲染**：预览的就是上传用的纯净正文，`#`、`**`、`-` 会原样显示（与「一键复制纯净正文」粘贴到平台后的结果一致）。
- 不做真实平台仿真（起点/番茄/微信读书各有排版），只做通用阅读器排版。
- 不做翻页动画、手势仿真、字号滑杆与自定义字体。
- 不持久化预览偏好，不新增设置项。
- 不改真机上的手机版布局（`body.wt-mobile`）与既有 `toggleMobilePreview()` 桌面预览机制的归属。
- 不做预览导图、不做整本书连续滚动阅读。

## 6. 影响面与约束

- 模块归属：编辑台（UI Shell）→ `UiShellActions` 新增端口 → Host（`main.ts`）装配 → 新 UI 文件 `src/mobilePreview.ts`；不新增 Feature Module、不新增 Service。见宪法 #4、架构说明 §5。
- 数据与设置：无变化，`data.json` 不新增键；预览的三组偏好只存内存。见宪法 #5。
- 命令面：不新增命令，入口放在编辑台书头与菜单。见宪法 #3。
- 文本管线：把 `copyCleanChapter` 的载荷处理抽成 `cleanChapterText()` 共用；**不得改变现有复制行为**（含去行尾空白与收尾空行）。
- 样式与手机端：新增 `.wt-phone-*` 一段样式，只服务桌面弹窗；不改既有搜索/分卷/移动端规则。渲染与观感只能靠截图与人工回归确认。见宪法 #8、#12。
- 自动检查：新增 `tools/checks/check-mobilepreview-module.js` 并注册进 `run-all.sh`，需要反向验证。
- 回退成本：无数据迁移；移除入口按钮即可停用；`git revert` 本次提交即可完全回退。

## 7. 开放问题

| 问题 | 结论 |
| --- | --- |
| 预览用「纯文本」还是「渲染后的 Markdown」 | 纯文本：与上传内容一致。「渲染后」是 Obsidian 里的观感，会掩盖平台上的真实样子 |
| 是否顺便把桌面端的 `wt-mobile` 布局预览一起做入口 | 不做，两件事目的不同（一个是作者工具形态，一个是读者阅读形态），混在一起会误导 |
| 预览偏好要不要记住 | 不记。本次不引入设置项与 `data.json` 变更，避免为了观感工具动数据面 |
