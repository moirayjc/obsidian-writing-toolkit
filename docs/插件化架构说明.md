# Writing Toolkit 插件化架构说明

> 面向对象：后续接手本插件的维护者与 AI Agent。
> 状态：已采纳（2026-10-17）。
> 本文定义目标架构和硬约束，不替代《插件设计文档》中的具体实现说明与踩坑清单。
> 开始迁移时，另读《插件化迁移计划》。
>
> 最短阅读路线：先读 §0–§3、§13–§14；需要设计或实现模块时，再读 §4–§12。

---

## 0. 一页结论

Writing Toolkit 永远是一个 Obsidian 插件，但内部采用 **Host + Services + Feature Modules** 的插件化架构。

- 用户只安装一个 `writing-toolkit`，只更新一个插件，只配置一个设置入口。
- 功能模块是内部代码单元，不是 Obsidian Plugin；用户不能单独安装或卸载模块。
- 第一阶段采用构建期静态组合：所有模块都打包进同一个 `main.js`，不运行外部功能包。
- 模块化的目标是缩小改动面和故障半径，不是提供安全沙箱。
- `main.ts` 的长期职责是启动 Host 和装配模块，而不是继续堆放功能逻辑。
- `data.json` 由 Host 统一读写；功能模块只能使用自己的数据命名空间。
- 新增功能优先进入 Feature Module；不要继续把注册面和状态堆进 `main.ts`。

一句话：**一个 Obsidian 插件，内部是一套可组装、可测试、可逐步拆分的写作功能系统。**

## 1. 术语

| 术语 | 含义 |
| --- | --- |
| Obsidian Plugin | 用户实际安装的单元：`manifest.json` + `main.js` + `styles.css`，本仓库只有一个 |
| Host | 插件内部宿主：启动、模块注册表、生命周期、事件、持久化、错误边界和清理 |
| Service | Host 提供给模块的稳定基础能力，例如作品索引、字数统计、设置、存储、编辑器适配 |
| Feature Module | 内部功能模块，例如批注、快照、章纲、番茄钟；有独立边界和生命周期 |
| UI Shell | 承载页面的稳定外壳，例如主页、编辑台、侧栏；通过插槽组合功能模块 |
| Effect / Disposable | 一次可撤销的注册，例如命令、监听器、定时器、DOM 事件、编辑器扩展 |
| Feature Flag | 用户设置中的功能开关；控制模块是否启动，不等于安装/卸载 Obsidian 插件 |
| Module Descriptor | 内部模块描述信息（id、依赖、设置 schema 等），不是 Obsidian 的 `manifest.json` |

文档中凡说“插件”，默认指 Obsidian Plugin；凡说“模块”，默认指 Feature Module。

## 2. 产品硬约束

这些约束优先于实现偏好，不得为了“架构更漂亮”而破坏：

1. **单插件安装**：用户只安装一个 `writing-toolkit`，不能要求安装第二个 Obsidian 插件。
2. **单次更新**：版本发布仍是一个插件包、一个 `manifest.json`、一个 `main.js`、一个 `styles.css`。
3. **开箱即用**：默认组合沿用当前版本的产品默认值；模块开关是高级选项，不应要求用户先配置模块。
4. **手机端可用**：`manifest.json` 的 `isDesktopOnly: false` 是现有产品承诺，模块不得无边界地依赖 Node/Electron。
5. **数据安全**：不能因为拆模块而改变用户数据的读写语义；任何数据格式变化都必须有迁移和备份流程。
6. **单一设置入口**：用户仍从插件设置页管理功能，不出现“模块也有自己的 Obsidian 插件设置”。
7. **命令面板四入口**：Command + P 中，本插件永远只出现「打开主页 / 打开工具箱 / 打开编辑台 / 打开设置」四条命令。新增功能、格式命令、批注操作、自检、调试入口、移动端预览、章节重编号和数据清理等，一律不得注册成 Obsidian 命令；入口应放在三个主页面、侧栏、右键菜单、设置页或编辑工具条里。这不是“尽量少”，而是永久产品约束，`check-commandsurface.js` 会拦住第五条命令。

## 3. 目标与非目标

### 3.1 目标

- 让一个功能的代码、数据、设置和生命周期有明确归属。
- 让低耦合功能可以独立开发、测试、启停和回滚。
- 让 `main.ts` 从“主类 + 全部业务”逐步变成装配入口。
- 让一个模块的启动失败或事件回调异常尽量不拖垮整个插件。
- 保持单插件安装、手机端、一键使用和现有数据兼容。

### 3.2 非目标

- 不拆成多个 Obsidian 插件。
- 不在第一阶段实现运行时下载、安装或加载外部功能包。
- 不把 Obsidian 内部的 `app.plugins` 当作嵌套插件管理器。
- 不追求“所有核心服务都可替换”；稳定服务是产品资产，不是负债。
- 不承诺所有模块都能在任意时刻热插拔。第一阶段至少保证启动时按开关装配，以及完整的卸载清理。
- 不把插件化当作安全沙箱；它不能自动阻止死循环、内存泄漏或全局副作用。
- 不在纯结构调整期间顺手更换 `data.json` 格式。

## 4. 目标结构

逻辑结构如下：

```text
Obsidian
└─ writing-toolkit（唯一安装单元）
   ├─ Host
   │  ├─ 启动与关闭
   │  ├─ 模块注册表与依赖解析
   │  ├─ 命令、视图、Ribbon、状态栏注册
   │  ├─ 编辑器扩展组装
   │  ├─ 事件适配与错误边界
   │  └─ Effect/Disposable 统一回收
   ├─ Services
   │  ├─ projectIndex / chapterPaths
   │  ├─ settings / persistence
   │  ├─ wordcount
   │  ├─ editor adapter
   │  ├─ UI slots
   │  ├─ diagnostics / logging
   │  └─ vault / workspace event adapters
   ├─ Feature Modules
   │  ├─ comments
   │  ├─ snapshots
   │  ├─ outlines
   │  ├─ pomodoro
   │  ├─ formatting / typography / hemingway
   │  └─ calendar
   └─ UI Shells
      ├─ home
      ├─ workbench
      ├─ sidebar
      └─ statusbar / mobile statusbar
```

建议的物理目录只表达依赖方向，不代表要求一次性搬完：

```text
src/
├─ main.ts                 # Obsidian 入口；只做 Host 启动和模块装配
├─ uiShellContext.ts       # UI Shell 的窄宿主上下文（Services 子集 + 显式端口）
├─ uiShellShared.ts        # UI Shell 共享纯工具与只读缓存
├─ host/                   # 生命周期、上下文、注册表、错误边界
├─ services/               # 稳定共享能力
├─ features/               # 功能模块
├─ views/                  # UI Shell 与视图
└─ shared/                 # 纯工具、类型、常量
```

迁移时必须**逐步引入**这些边界，不能为了目录整齐做大规模搬文件和重写。

## 5. 职责边界

### 5.1 Host

Host 负责：

- 接收 Obsidian 的 `onload` / `onunload`。
- 创建共享 Services 和模块上下文。
- 读取模块描述与功能开关，按依赖顺序启动模块。
- 统一注册命令、视图、Ribbon、状态栏、设置页和编辑器扩展。
- 记录并回收模块产生的所有 Effect。
- 捕获模块启动、事件回调和清理过程中的异常。
- 提供诊断信息，例如已启用模块、失败模块和注册数量。

Host 不负责：

- 具体业务规则，例如批注如何定位、快照如何生成。
- 某个功能自己的数据结构、视图布局和交互细节。
- 直接读写模块内部状态。

### 5.2 Services

Services 是稳定的共享能力，建议优先抽出：

| Service | 职责 |
| --- | --- |
| `project` | 作品识别、章节路径、章节排序、作品索引失效与重建 |
| `wordcount` | 文本计数模式、格式剥离、统一计数入口 |
| `settings` | 设置读取、默认值合并、保存入口和设置变更通知 |
| `persistence` | `data.json` 的唯一读写入口、串行保存、迁移与备份提示 |
| `events` | 带类型的 Vault / Workspace / DOM / 布局事件、定时器与作用域清理；不是通用事件总线 |
| `editor` | Editor/CodeMirror 适配、扩展注册和刷新入口 |
| `ui` | 视图插槽、面板挂载点、菜单和通用 UI 注册 |
| `diagnostics` | 计数、耗时、最近值、错误历史和模块状态快照 |

Service 的接口应表达能力，而不是暴露某个模块的内部实现。

`settings` Service 的迁移期契约位于 `src/settingsSchema.ts` 和
`src/services/settingsService.ts`。Service 负责默认值合并、旧格式恢复、
读取和变更通知，但磁盘写入仍先经过插件兼容保存入口。设置页可以直接修改
返回的实时设置对象；写盘后必须调用 `publishChanges()` 广播变更。后续模块
应优先调用 `set()` / `update()`，不要自行复制默认值或维护第二份设置状态。

`editor` Service 的迁移期契约位于 `src/services/editorService.ts`。它统一
读取活动编辑器、校验编辑器引用、访问 Obsidian 未公开类型的 `Editor.cm`、
从 `editorInfoField` 读取文档路径、调用 `EditorView.findFromDOM()`，并负责
编辑器扩展注册与 `workspace.updateOptions()` 刷新。按功能需要，它还提供
`getMarkdownEditorViews()`，把 Workspace 遍历收口成只读 `EditorView[]`，
供需要逐编辑器同步状态效果的模块使用。`HostRegistrationApi` 的
`registerEditorExtension()` 现在只做转发，`main.ts` 不再直接摸这些
CodeMirror / Workspace 细节。原来的单函数适配文件 `src/editorView.ts`
已由该 Service 取代。

`ui` Service 的迁移期契约位于 `src/services/uiService.ts`。它统一负责视图
注册、按类型查询 leaf、创建左右主区 leaf、显示并聚焦视图、展开侧栏、手机
抽屉迁移和插件设置页入口。`HostRegistrationApi.registerView()` 只做转发；
`main.ts` 不再直接操作 `workspace.getLeavesOfType()`、左右 side split、
`setViewState()`、`detach()` 或内部设置窗口。UI Service 只提供稳定的界面
挂载能力，不承载具体页面的业务状态。

`events` Service 的迁移期契约位于 `src/services/eventsService.ts`。它提供
带类型的 Vault / Workspace / DOM 订阅、布局就绪回调、`setTimeout()` /
`setInterval()` 和统一 `dispose()`；每个作用域只清理自己的订阅与定时器，
回调异常按作用域 owner 记录并隔离。Host 激活模块时创建
`writing-toolkit:<module-id>` 事件作用域，并把其清理函数挂入模块的
`EffectScope`；Host 最终销毁时再关闭 Events Service。`main.ts` 使用
`writing-toolkit:main` 主作用域，`MobileStatusBar` 使用自己的
`writing-toolkit:mobile-status-bar` 作用域。

第一版 Events Service 刻意不做通用事件总线：设置变更仍由 Settings Service
的 `subscribe()` / `publishChanges()` 负责，CodeMirror 事件仍归 Editor
Service 与编辑器扩展生命周期，视图内部的 DOM 事件仍随视图自身生命周期
清理。章纲已迁入 `outlines` 模块，Vault / Workspace 事件由模块统一经
`FeatureContext.events` 订阅；面板自身只保留随组件生命周期清理的定时器与
渲染守卫。新模块不得复制直接 `.on()` / `.offref()` 订阅。

`FeatureContext.registrations` 的类型是 `FeatureRegistrationApi`，即从
`HostRegistrationApi` 中移除 `registerEvent`、`registerDomEvent` 和
`registerInterval` 后的收窄接口。Feature Module 可以经它注册命令、视图、
Ribbon、状态栏、设置页和编辑器扩展，但插件级事件与定时器必须走
`FeatureContext.events`；类型层面会阻止模块绕过 `EventScope` 保留无法
按模块撤销的监听器。

`diagnostics` Service 的契约位于 `src/services/diagnosticsService.ts`。
它不依赖 Obsidian，提供计数、耗时聚合、最近值、有限错误历史和模块状态
快照；`snapshot()` 返回副本。Host 是模块生命周期状态的唯一来源，负责把
`active` / `failed` / `inactive` 投影给 Service，并记录模块启动、停用与清理
错误。Feature Module 可以通过 `FeatureContext.services.diagnostics` 记录通用
结构化事实。旧 `src/diagnostics.ts` 继续承载批注、统计和格式等领域自检报告，
不并入通用 Service。

### 5.3 Feature Modules

Feature Module 负责：

- 自己的领域规则和内部状态。
- 自己的命令、视图、菜单、设置项和事件订阅。
- 通过 Host 提供的上下文访问基础能力。
- 在停用时撤销自己产生的一切副作用。

当前模块群的大致归属建议：

| 模块 | 当前相关文件 | 归属建议 |
| --- | --- | --- |
| 批注 | `comments.ts`、`commentStore.ts`、`commentDecor.ts`、`commentView.ts`、`features/commentsModule.ts` | `comments`，已迁移 |
| 快照 | `snapshot.ts`、`snapshotDiff.ts`、`snapshotPanel.ts`、`features/snapshotModule.ts`、`features/snapshotUiModule.ts` | `snapshots.core` + `snapshots.ui`，均已迁移 |
| 章纲 | `outlineText.ts`、`chapterOutline.ts`、`outlineModal.ts`、`features/outlineModule.ts` | `outlines`，已迁移 |
| 番茄钟 | `pomodoro.ts`、`pomodoroWidget.ts`、`features/pomodoroModule.ts` | `pomodoro`，已迁移 |
| 格式工具条/包裹 | `formatToolbar.ts`、`formatWrap.ts`、`features/formatToolbarModule.ts` | `editor.format-toolbar`，已迁移；包裹纯函数仍共享 |
| 硬换行 | `hardBreak.ts`、`features/editorHardBreakModule.ts` | `editor.hard-break`，已迁移 |
| 标点辅助 | `punctuation.ts`、`features/editorPunctuationModule.ts` | `editor.punctuation`，已迁移 |
| 打字机与段落高亮 | `typewriter.ts`、`features/editorTypewriterModule.ts` | `editor.typewriter`，已迁移 |
| 海明威模式 | `hemingway.ts`、`features/editorHemingwayModule.ts` | `editor.hemingway`，已迁移 |
| 排版与主题 | `typography.ts`、`themeSnippet.ts`、`features/typographyModule.ts` | `appearance.typography`，已迁移 |
| 日历 | `calendar.ts`、`features/calendarModule.ts` | `calendar`，已迁移 |
| 主页、编辑台、侧栏 | `home.ts`、`workbench.ts`、`sidebar.ts` | UI Shell，只依赖 Services 与 `UiShellContext` |
| 状态栏 | `statusbar.ts`、`mobileStatusBar.ts` | UI Shell，只依赖 Services 与 `UiShellContext`；`statusbar` 只用 WordCount Service |

这些是边界建议，不是要求按文件名机械拆分。批注这类跨编辑器、存储、侧栏的能力应保持为一个完整模块，内部再分文件。

`editor.punctuation` 是最小完整样例：模块读取并订阅 `punctuationAssist`，
把输入处理器注册到 Editor Service，把取消订阅和状态清理挂进 `EffectScope`；
`main.ts` 只保留旧 UI 的兼容桥。阶段 4 已进一步把番茄钟和日历的高耦合部分
拆成模块：番茄钟拥有计时器、历史、自动快照和设置订阅；日历拥有实例生命周期
与设置热更新；状态栏、手机状态条、侧栏和主页只通过窄接口取状态或挂载面板。

`editor.hard-break` 沿用同一模式：模块读取并订阅 `hardBreakOnEnter`，把回车
扩展注册到 Editor Service，纯输入变换通过闭包读取模块状态；旧设置 UI 仍经
`main.ts` 兼容桥即时启停，但模块停用后兼容桥不能重新唤醒它。

`editor.typewriter` 把三项设置、三个 `ViewPlugin` 和运行时状态收进同一模块：
`typewriterMode` 控制底部留白与输入后的滚动，`typewriterOffset` 控制目标位置，
`immersiveParagraphHighlight` 独立控制当前段落装饰。模块通过
`TypewriterRuntime` 闭包向插件读取实时状态，不保存模块级可变全局变量；设置
改变时由 Editor Service 刷新现有编辑器，停用时取消待执行动画帧并清理留白。

`editor.hemingway` 通过 CodeMirror `Facet` 把模块运行时闭包注入 StateField，
不再持有模块级期望状态。事务过滤、光标守卫和历史键位统一读取
`active && enabled`；模块通过 `getMarkdownEditorViews()` 向现有编辑器同步
状态效果，停用时取消待执行动画帧并关闭所有编辑器。`Mod-z`、`Mod-Shift-z`、
`Mod-y` 由最高优先级守卫接管，避免 Obsidian 的撤销/重做路径绕过事务过滤。

`editor.format-toolbar` 负责工具条开关、三种生效范围、设置签名刷新和编辑器
扩展注册；`allowsPath()` 同时供右键批注入口与格式诊断复用。批注按钮通过
回调交给已迁移的 `comments` 模块，工具条模块不反向拥有批注业务。

`appearance.typography` 负责六项排版设置、配色主题缓存、首帧预热入口和
`.obsidian/snippets/wt-theme-tone.css` 同步。`main.ts` 只保留“在任何 `await`
之前调用模块预热方法”这一条时序约束；设置变化与卸载清理都由模块自己的
Settings 订阅和 `EffectScope` 管理。

`snapshots.core` 接管快照管理器的生命周期：模块创建 `DraftSnapshotManager`，
用自己的 EventScope 订阅编辑器变化、活动文件切换与重命名，注册 30 秒心跳，
并在 EffectScope 销毁时结束当前会话。`snapshots.ui` 通过稳定的侧栏插槽挂载
面板与差异窗口，只使用 `snapshots.core` 的窄操作端口；UI Shell 不再认识
快照管理器或面板实现。

### 5.4 UI Shell

UI Shell 负责页面结构和插槽，不应该成为业务状态的第二个中心。

- `home`、`workbench`、`sidebar` 与 `mobileStatusBar` 构造时只接收
  `UiShellContext`（`src/uiShellContext.ts`）：`services` 是 Services 子集，
  `stats` / `prefs` / `nav` / `recent` 是读写端口，`caps` 是章纲、快照、批注、
  日历与番茄钟的窄操作端口，`editorOptions` / `actions` 是编辑辅助设置与宿主动作。
- 功能入口通过 UI 插槽挂载；Shell 不 import `main.ts`、不 import `features/`
  实现，也不互相 import。
- `statusbar` 只依赖 `WordCountService`，不需要 Shell 上下文。
- `home` / `workbench` / `sidebar` 共享的纯展示工具与只读缓存集中在
  `src/uiShellShared.ts`，不构成 Shell 之间的依赖。

## 6. 模块契约

下面是当前模块上下文与注册面的契约示意：

```ts
export type FeatureRegistrationApi = Omit<
  HostRegistrationApi,
  "registerEvent" | "registerDomEvent" | "registerInterval"
>;

export interface FeatureModule {
  readonly id: string;
  readonly dependsOn?: readonly string[];
  activate(ctx: FeatureContext): void | Promise<void>;
  deactivate?(): void | Promise<void>;
}

export interface FeatureContext {
  readonly app: App;
  readonly services: HostServices; // 包含 diagnostics / editor / events / persistence / project / settings / ui / wordcount
  readonly registrations: FeatureRegistrationApi; // 命令、视图、Ribbon、状态栏、设置页、编辑器扩展；不含事件和定时器注册
  readonly events: EventScope; // 模块级作用域，由 Host 绑定到 EffectScope
  readonly effects: EffectScope;
  readonly log: HostLogger;
}
```

### 6.1 激活

1. Host 检查模块依赖是否满足。
2. Host 为该模块创建独立的 Effect Scope，并创建绑定到该 Scope 的模块级
   `EventScope`。
3. 模块通过 `ctx.registrations` 注册命令、视图等稳定注册面，通过
   `ctx.events` 注册事件、DOM 监听和定时器，并通过 `ctx.effects` 回收普通资源。
4. 激活失败时，Host 回滚该模块已注册的 Effect，并记录模块 id。
5. 不要因为一个可选模块失败，就让整个插件无法启动。

### 6.2 停用

- Host 按相反顺序撤销 Effect。
- 模块必须保证重复停用不会重复删除全局资源。
- 定时器、DOM 事件、Vault 事件、Workspace 事件和 CodeMirror 扩展必须在停用时清理；
  其中前三类通过模块 `EventScope` 统一回收。
- 第一阶段至少保证插件卸载和重新加载时不残留注册；完整热插拔另行验证。

### 6.3 依赖

- 模块通过 `dependsOn` 声明依赖，不靠 import 顺序或手工启动顺序。
- 依赖缺失时，模块应明确失败并被记录，而不是静默半启动。
- 模块 id 一旦发布，应保持稳定，避免设置和诊断记录迁移困难。

## 7. 注册与生命周期规则

### 7.1 统一注册

Feature Module 不得各自创建一套全局注册机制。命令、视图、Ribbon、状态栏和
设置页通过 Host 的注册 API 创建；Vault / Workspace / DOM / 布局事件和插件级
定时器通过 `FeatureContext.events` 创建，并返回统一的 disposer。视图内部的
DOM 事件可以跟随视图生命周期管理，但不能伪装成跨模块事件总线。

为防绕过，`FeatureContext.registrations` 使用 `FeatureRegistrationApi`，
显式移除 `registerEvent` / `registerDomEvent` / `registerInterval`。需要撤销的
事件与定时器不得塞回模块的普通 Effect，否则失败启动或停用时就无法保证按模块
作用域完整回收。

### 7.2 编辑器扩展

- 编辑器扩展的最终组合顺序由 Host 决定。
- 模块只能提供自己的扩展配置或扩展实例，不应直接修改其他模块的 EditorState。
- 需要动态启停编辑器扩展时，由 Host 统一选择刷新策略；模块不要各自发明一套全局变量和 `updateOptions()` 约定。

### 7.3 UI 与样式

- 新模块的 CSS 类使用 `wt-<module>-` 前缀；现有 `wt-` 类不要求为了插件化大规模重命名。
- 模块不得写无作用域的全局选择器。
- 模块挂载的 DOM 必须由模块或统一 UI 服务负责移除。
- 页面 Shell 只负责插槽和布局，不直接实现模块业务。

### 7.4 错误边界

Host 至少应捕获：

- 模块 `activate()` / `deactivate()` 的异常。
- 模块事件回调的同步异常。
- 异步任务中未处理的异常（能捕获的部分）。

记录内容至少包括模块 id、阶段和错误信息。Events Service 负责为事件回调和
定时器回调补充作用域 owner，并隔离单个回调的同步/异步异常；一个模块失败
后，Host 可以将其标记为失败并跳过后续启动；是否自动停用其 UI 入口由 Host
决定。

Host 同时把模块三态和带模块 id 的启动、停用、清理错误投影到 Diagnostics
Service。通用诊断只保存结构化事实；面向人的领域报告仍留在各自的
`diagnostics.ts` / 功能模块中。

## 8. 数据与设置

### 8.1 唯一写入者

`data.json` 只能由 Host 的 Persistence Service 写入。模块不得直接调用 `saveData()`，否则多个模块的并发保存会互相覆盖，且无法统一迁移。

当前实现为 `src/services/persistenceService.ts`：读取、写入和 `flush()`
都经过同一个 Service；每次保存先冻结 JSON 快照，再进入串行队列。
写入失败只拒绝当次调用，后续写入仍会继续。迁移期 `main.ts` 仍负责拼装
现有数据对象，但不再直接调用 Obsidian 的 `loadData()` / `saveData()`。

### 8.2 数据命名空间

- 每个模块拥有自己的逻辑命名空间，例如 `modules.snapshots`。
- 迁移期可以继续使用现有顶层数据结构，但新代码必须先设计命名空间和迁移路径。
- 禁用模块时保留其数据，不能因为关闭功能就删除用户数据。

### 8.3 设置

- 默认值必须由 Host 统一合并，不能因为新增模块而丢失旧配置。
- 模块设置项通过描述信息注册到设置页；设置页的布局仍归 Host/UI Shell。
- 设置变更通过 Settings Service 的订阅/广播机制通知相关模块，模块自行决定
  是否热刷新；第一版不为此新增通用事件总线。

### 8.4 伴随文件

批注、章纲和快照等伴随文件属于对应模块的领域数据：

- 模块负责自己的路径规则、序列化和解析。
- 文件重命名、移动、删除时必须清理或迁移关联状态。
- 不直接修改正文，除非功能本身明确要求并经过现有安全流程。
- 跨模块需要伴随文件能力时，通过模块公开的 Service，而不是 import 内部实现。

### 8.5 数据兼容

插件化不是更换数据格式的理由。纯结构调整期间：

- 不重命名已有 `data.json` 字段。
- 不移除旧字段，除非同时写迁移和回滚说明。
- 构建候选版本并加载前，按《插件设计文档》§6.5 备份 `data.json`。

## 9. 依赖规则

### 9.1 允许

- Feature Module 依赖 Host、Services 和 `shared/` 中的稳定类型/纯工具。
- 模块依赖另一个模块的公开 Service 接口，并且依赖关系在模块描述中声明。
- UI Shell 依赖 Services 与 `UiShellContext` 的窄端口。

### 9.2 禁止

- Feature Module 直接 import `main.ts`。
- Feature Module 直接 import 另一个 Feature Module 的内部文件。
- 通过修改全局对象、DOM 或模块级变量来“通知”另一个模块。
- 为了省事把业务状态重新放回 `main.ts`。
- 新增运行时外部代码加载，除非另行更新本文并完成安全、版本和移动端评估。

### 9.3 当前已知债务

阶段 6 债务收口后，UI Shell 层已无已知架构债务：

- `stats`、`prefs`、`nav` 的实现分别在 `services/statsService.ts`、
  `services/workspacePrefsService.ts`、`services/navigationService.ts`；
  `main.ts` 只保留兼容包装与接线，Host Context 的端口直接由 Service 实现。
- `statusbar` 只订阅一次 `StatsService`；统计数字由宿主结算后调用 `publish()`，
  不再由 `main.ts` 手写 `setState` 扇出。
- `CalendarHandle` 定义在 `services/uiTypes.ts`；三个视图 id 常量在 `uiSlots.ts`，
  UI Shell 与导航 Service 都不需要 import 功能模块或彼此的实现。
- 剩余事项属于发布流程（手机真机回归、回滚演练、commit/tag/push），不是代码债务。

## 11. 故障隔离的边界

插件化可以做到：

- 一个模块启动失败时，Host 有明确记录并阻止其继续注册。
- 一个事件回调抛错时，记录模块 id 并避免错误扩散到其他回调。
- 一个模块停用时，自动撤销它注册的命令、视图和监听器。

插件化不能自动做到：

- 阻止无限循环、超大计算或同步阻塞。
- 回收模块遗留的全局对象引用或内存泄漏。
- 隔离所有 CodeMirror/EditorState 副作用。
- 阻止模块修改原型、全局 DOM 或 Obsidian 内部对象。

因此，模块边界和 code review 仍然重要；不要用“已经插件化”替代测试和人工验证。

## 12. 迁移原则

1. **先服务、后模块**：先把作品索引、字数、设置、持久化等共享能力抽稳，再拆功能。
2. **先低耦合、后高耦合**：先迁纯工具或小模块，批注这类横跨编辑器、存储、侧栏的功能最后迁。
3. **一次一个模块**：每个阶段都保持可构建、可运行、可回滚。
4. **保持行为不变**：结构迁移不顺手重写 UI、样式和业务规则。
5. **向后兼容数据**：任何格式调整都必须有迁移、备份和回滚路径。
6. **默认功能不减少**：用户升级后不应突然失去已存在的功能。
7. **Host 变薄，不变成新单体**：Host 只做编排和基础能力，不吸收各模块业务。
8. **文档随契约更新**：架构变化先更新本文，再改实现；实现与本文冲突时，不要默默绕开。

## 13. 已作出的架构决定

| 决定 | 结论 |
| --- | --- |
| 安装形态 | 永远一个 Obsidian 插件，一键安装、一次更新 |
| 模块形态 | 内部 Feature Module，静态打包进同一个 `main.js` |
| 第一阶段加载方式 | 构建期组合 + 启动时功能开关 |
| 运行时外部模块 | 暂缓；不是当前产品目标 |
| Obsidian `app.plugins` | 不作为内部模块加载器 |
| Cordis/DeepSeek Harness | 借鉴 service、依赖、事件、可逆 Effect 思想，不直接引入框架 |
| 事件模型 | 第一版只做带类型的生命周期作用域，不做通用事件总线；设置、CodeMirror 和视图局部事件各归其所有者 |
| 诊断模型 | Host 负责模块三态与生命周期错误的事实投影；Feature Module 记录自己的结构化事实；领域报告继续由 `src/diagnostics.ts` 生成 |
| 数据格式 | 迁移期保持现有 `data.json` 结构；命名空间另立迁移计划 |
| 默认组合 | 现有功能默认启用，模块开关只作为高级能力 |
